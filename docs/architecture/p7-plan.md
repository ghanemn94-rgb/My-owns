- **Two gate systems.**
  - G1–G6 are business approvals inside the product. DG0–DG7 are engineering delivery gates.
  - Nothing in P7's product code reads or writes the engineering records. The release tooling (§4.1) reads them, but only outside the product runtime.
  - Product G6 never implies DG7. DG7 never implies any G1–G6 approval.
  - No agent grants a real business, Finance or IT approval. A retention period, recovery objective, orchestration target or identity mapping in this plan is a **configuration slot that Mobily IT fills**. No P7 task claims that IT agreed to anything.
- **Honest live-integration status (binding).** These cannot be exercised live in this sandbox: the enterprise IdP, an IT object store, mail or enterprise messaging, an external or internal AI model endpoint, corporate data sources, an IT orchestration target and an artifact mirror. Each keeps its P6 contract, test adapter and documented residual (`environment.md` l.81–110). P7 adds no live claim. The final handover lists each one as an external configuration dependency (M0414: "the remaining external configuration dependencies").
- **Carried rules (D-078 §3, D-088 §2, D-141, D-193), binding on every P7 task:**
  - shared free-text rules and strict UTF-8. Migration manifests and configuration bundles are UTF-8 JSON, refused otherwise;
  - commit-time re-authorisation, and no remote I/O inside a transaction. An evidence-byte copy, an export file write or an archive write happens before or after the transaction and is recorded through the outbox;
  - exactly-once jobs with advisory locks and unique backstops. This covers the archival job, the migration import and the bundle import;
  - decimal-only arithmetic. Unknown/Stale/n/a is never 0 or green. A transferred `numeric` value travels as its exact decimal string, never as a JSON number;
  - bilingual text translated at render time, and true for the release it ships in. A P7 string that says "planned" or "not available" changes in the task that ships the feature (F-DG4-160);
  - one form-level alert per form; session-bound web actions;
  - harness ports below 32768 (pool 25000–31999, `tests/qa/support/pg-port.sh`), verification with the locale unset and with `C.UTF-8`, tests deterministic under load with explicit budgets;
  - every non-zero exit disclosed; ADR claims enumerated and exactly true;
  - D-193: full 40-hex ids in assignments; no candidate file changes after a freeze; `runs/**` and `reviews/**` never moved or deleted; the full e2e runs on the merged tree before every freeze.

## 1. Inventory: the 54 DG7 requirements, one slice each

### 1.1 The slices

The P7 row (l.619) names eight outputs. This plan keeps each one as a slice, with five changes:

- **The data migration is split from the configuration transfer** (C and D). REQ-S19-014 and REQ-S19-016 move a whole installation's records with their ids. REQ-S19-008 moves published configuration by stable key into an installation that already has its own records. The two need different identity rules, which is reason enough to keep them in separate ADRs. They still share one architecture task (§4).
- **Schema, API and connector handover documentation is its own slice (F).** Handover items 3 and 4 (§19 l.554–555) have acceptance texts that are **coverage checks**: "the data dictionary covers every table and column", "every endpoint and connector … passes its contract test". They are not prose guides.
- **Security controls evidence and secret hygiene form one slice (G).** REQ-S16-031 (secret scan, TLS and encryption integration) and REQ-S16-033 (no compliance claim; a control-to-test matrix) are scans and matrices over the same payload.
- **The delivery-protocol rows split into J and K.** J holds the 16 recurring gate obligations, which the DG7 gate proves by existing. K holds the three drill and test-level rows, which need new runs: A26, A27 and the per-gate test-level index.
- **Final verification (L) is kept apart from sealing (M).** L is what DG7 approves. M runs after approval (l.621).

- **Critical path:** ARCH-02 (C + D) → BE-C export → BE-D import → BE-E evidence bytes → DO-D transfer drill → QA-C (A18) → freeze → DG7 → M. The transfer drill (REQ-S19-017) is the integrating proof of the stage. It needs a working export and import, the readiness extension, the deployment guide and the archive.
- **Second path:** ARCH-03 (E) → DO-F backup/restore → QA-C (A19). E depends on C only for the attachment manifest format, which ARCH-02 fixes before ARCH-03 runs.
- **Off the critical path:** A and G (tools and scans, early), F (needs the final schema and contract, so late but short), I (the register snapshot needs AN-P7's final register; the API and screen land early against the current file), J (tool early; its DG7 run is after the gate), K (A26 is early, so its repair cycle does not crowd the freeze; A27 can run at any checkpoint).
- **M after everything.** It is the only work after approval. Its **tooling** is built and reviewed before the freeze, because a tool written after approval would be unreviewed code that decides delivery.
- **No module cycle.**
  - `transfer` reads every table through a **catalogue-driven** export plan derived from `information_schema` and the FK graph. It imports no domain module.
  - `transfer` writes only through the owner-role CLI path, never through `mth_app`.
  - `retention` asks each owning module through a `RetentionClassRegistry` port (the P5 `AutomationActionRegistry` pattern), so `retention` imports no domain module.
  - `release` reads a build-time register snapshot and imports nothing.

## 4. Architecture tasks

Each task is sized for about 2 hours of architect work and runs alone on the shared contract files (§5.3). It writes:

- its ADRs;
- its migrations with the P2 guard pattern and a guard probe on a real PostgreSQL;
- the Kysely types and catalogue pins;
- its `P7_PERMISSIONS` additions;
- its OpenAPI operations, checked with `openapi:lint`;
- the ERD, data-dictionary and permissions-matrix sections;
- its `p7-work-split.md` section: owners, seams, pending lists, problem codes and exact English texts.

Implementers of a slice start only after its ARCH task is merged.

- **Migration numbering.** `0001`–`0130` exist, with eight retired gap ids that are never filled. Each task owns a contiguous range from `0131`. The architect writes from the low end, and the rest of a range is for that slice's implementers. `0158`–`0163` are held by the orchestrator for repairs.
- **Advisory-lock classes** (ADR-0016 §6 registry, `platform/advisory-locks.ts`; P6 used up to 730327, and 730328–730339 are held by the orchestrator). Each task owns a disjoint block from 730400. A class a task does not need stays reserved and is never reused by another block. 730428–730439 are held by the orchestrator for P7 repairs.
- **ADR numbers** run ADR-0062…ADR-0074 in the order below. A task that needs fewer ADRs leaves its numbers unused rather than shifting later numbers. Each ADR verifies current official documentation, support windows and licences before pinning any new dependency, and records that evidence. **No new runtime dependency is expected in P7.** Archive, checksum, tar and JSON work uses Node built-ins and the existing pinned toolchain. A new dependency is recorded BLOCKED if it cannot be verified offline (D-057).

### 4.1 The A28 two-step (master prompt l.621), as ARCH-06 must specify it

1. **Build the payload, and freeze it.** Everything the handover needs is in the candidate before the freeze:
   - code, migrations and the contract;
   - `docs/handover/**`, the register and the release notes generated from it;
   - `tools/release/{build-archive,seal,verify-seal}.mjs` and their tests;
   - the final-report template.

   The orchestrator freezes with `node tools/gates/candidate.mjs --stage DG7`. The **payload hash is the DG7 candidate id**. The META_EXCLUDES in `tools/gates/lib/candidate.mjs` keep reviews, gates, test evidence, runs, candidates, handbacks, assignments, `findings.json`, `progress.md` and `stages.json` out of it.
2. **Rehearse before review.** DO-J runs `seal.mjs` on a **scratch clone** under `$TMPDIR` with a synthetic, clearly labelled `DG7.json`. It shows that `verify-seal.mjs` passes, and that it fails on each tampering case: a changed payload file, a missing gate record, a wrong agent-definition checksum, a register mismatch, and a DG record named as a G-gate or the reverse. The rehearsal evidence goes in DO-J's handback evidence. It never touches `docs/delivery/gates/`.
3. **Review and audit the payload.** Domain, code-security, QA, then the release audit. DG7 is APPROVED on that candidate id. A28 is **not** a prerequisite (M0411).
4. **Seal (orchestrator, after approval).** `node tools/release/seal.mjs --candidate <DG7 id>`:
   - re-derives the manifest from the DG7 `source_commit` and checks its hash equals the candidate id;
   - builds the payload archive from exactly those files (deterministic, ADR-0062);
   - writes the envelope manifest. The envelope lists:
     - the eight `gates/DG0–DG7.json`;
     - the ten `.claude/agents/*.md`;
     - `requirements.csv` and `findings.json`;
     - the review records each gate cites;
     - the drill reports;

     each with its SHA-256;
   - builds the envelope archive (payload archive + envelope files).
   - **Outputs:**
     - the manifest and the seal report go to `docs/delivery/test-evidence/DG7/seal/`. That path is META-excluded, so sealing never changes the payload hash, and `candidate.mjs --stage DG7` on the sealed tree still prints the approved id;
     - the archives go to a git-ignored `dist/release/`, with their checksums recorded in the seal report.
5. **Verify (A28).** `node tools/release/verify-seal.mjs` checks:
   - every listed file is present, and its checksum matches;
   - the payload hash equals `gates/DG7.json` `candidate_id`;
   - all eight gate records validate (`validate --stage DGx --historical` for each);
   - there are ten agent definitions;
   - the register in the archive equals the candidate's;
   - no DG record is labelled as a G1–G6 approval and no G record as a DG gate. This is a text and field check over the envelope, using the same term lists as the P6 seeded-text scan.

   It also re-hashes the archives and records the **archive checksum separately** from the payload hash, as l.621 requires.
6. **Outcome.**
   - If sealing or verification fails, delivery is **blocked**. The orchestrator records the failure, and a repair that changes any payload file requires a new candidate and new reviews (l.621).
   - A repair that touches only envelope inputs (for example a missing copy of a gate record) is re-sealed with no new review, because the payload hash is unchanged. The verify report shows the payload hash is the same.
   - Final delivery is declared only after verification passes. The final delivery report (REQ-DLV-031) is completed at this step.

    - `environment.md` l.91–93: "`docker info` exits 1 inside the agent sandbox";
    - l.40/l.60: the daemon was started manually in the orchestrator's session.
  - **Recommendation:**
    - agents deliver the scripts and run the container-free halves (clean start from the archive, transfer and offline drills in the no-network sandbox);
    - the **orchestrator** runs the Compose, image-load and Keycloak e2e halves on its host, outside the agent sandbox, with the logs committed as orchestrator evidence;
    - reviewers re-run what they can and record the rest BLOCKED with that reason.
  - **Decision needed:** whether an orchestrator-run container drill is acceptable evidence for A18, or whether it stays a disclosed BLOCKED residual, which would make it a **release blocker** under REQ-S21-003.
- **Q2. "separate app, infra, docs and demo-data directories" (REQ-S19-001).**
  - The repository keeps demo seed code in `packages/db/src/demo/**` (ADR-0050), inside the application.
  - **Recommendation:** the archive layout separates by **artefact**:
    - `source/` holds the complete repository at the candidate, unchanged so it builds;
    - `infra/` holds Compose, images and the environment template;
    - `docs/` holds the handover;
    - `demo-data/` holds the synthetic demo installation exported as a migration manifest.

    The repository layout is unchanged, because moving demo code would reopen DG5 for no behaviour gain. The orchestrator decides whether `source/` containing seed code satisfies "separate".
- **Q3. Retention periods and the meaning of "archive".**
  - REQ-S16-024 notes: "Retention periods must be agreed with Mobily IT; defaults are placeholders."
  - Its acceptance: "an archival job run on test data archives only records past retention and logs each action".
  - §16: "soft deletion is not a substitute for an approved retention policy".
  - **Recommendation:**
    - every class defaults to `retain` with period "not set (IT to agree)", so a fresh install archives nothing;
    - `archive` means the record is written to an archive set in the migration-manifest format (checksummed, in evidence storage) and its live row is marked archived and made read-only;
    - `archive_then_purge` is allowed in P7 only for operational classes (§3 seam 9). The test proves it on test data with test periods;
    - business records, audit and snapshots are never purged by P7 code.
- **Q4. Importing audit history verbatim** (§3 seam 8).
  - **Recommendation:**
    - import only into an empty database, by the owner role, through the CLI;
    - load rows verbatim, then write one `migration.imported` audit event with the manifest checksum.
  - If the orchestrator judges that this conflicts with ADR-0004's append-only rule, the alternative is to import audit history as an attached, read-only archive table. That fails "round-trip preserves … audit history" for the in-app audit view, so it needs a decision.
- **Q5. Identity rebind** ("rebind corporate identity subjects under IT control", l.562).
  - **Recommendation:**
    - users are imported with their (issuer, subject);
    - IT supplies a mapping file, and `mth db rebind-identity` applies it, audited. Users not mapped cannot sign in;
    - the administrator bootstrap path (`mth db bootstrap`) is unchanged and refuses on a non-empty database. A transferred installation therefore needs at least one mapped administrator before first sign-in, and the deployment guide says so.
- **Q6. Readiness semantics** (§3 seam 1). REQ-S19-010: "the readiness endpoint reports database, storage and worker status". **Recommendation:** storage gates readiness, and the worker is reported only, so an API is not withdrawn from the load balancer because the worker is down. Gating on storage is a DG1 reopen candidate.
- **Q7. Guide languages.**
  - The assignment says "operator, admin and user guides (EN/AR)". CLAUDE.md requires both languages "for every user-facing string", and guides are documents.
  - **Recommendation:**
    - user and admin guides in both languages;
    - IT and operator guides (deployment, backup, upgrades, automation operations) in English with an Arabic summary page;
    - every Arabic text not checked by a qualified reviewer is marked provisional.
  - **Decision needed** if full Arabic IT guides are required.
- **Q8. Where the seal tooling lives.**
  - `tools/gates/**` is implementer-protected. ARCH-06 puts sealing in `tools/release/**`, built and reviewed in the payload, and run by the orchestrator.
  - **Decision needed:** whether the orchestrator also wants `validate.mjs` to call `verify-seal.mjs`. That is a gate-rule change the orchestrator makes and reviewers review, and it is not needed for l.621.
- **Q9. Evidence paths named in the register.**

- **Q10. - **Q13. The protocol audit over approved history.**
  - DO-I's checks may find historic non-conformance in DG0–DG6 records: overlaps above four, an assignment missing an element, a `--historical` log not in test-evidence, or F-DG6-952-like ordering.
  - **Recommendation:** approved records are never rewritten. Each hit is reported to the orchestrator, and either (a) closed by an added record (for example copying an existing `--historical` log into `test-evidence/<DGx>/orchestrator/` with a note), or (b) accepted as an observation through the normal finding process.

- **Q14. Restore across PostgreSQL majors.** Local verification uses PostgreSQL 16 (`clean-start-local.sh`), and Compose pins `postgres:18`. **Recommendation:** the A19 drill restores into the same major it dumped from, and the guide states that a cross-major restore is an IT upgrade procedure (dump with the newer client).
- **Q15. "Secure administrator bootstrap"** (REQ-DLV-039). It exists (`bootstrap.ts`, `clean-start-local.sh` phase A). **Recommendation:** re-prove it in the DO-D clean environment, and document it in the deployment guide. No new code.
- **Q16. "no password hashes" (REQ-S19-016).**

- **Q17. "a different base URL" (REQ-S01-006, S19-017).**

  - Serving under a sub-path (`https://host/hub/`) is not claimed unless ARCH-04 finds the SPA and cookies already support it. Otherwise it is a known limitation.
- **Q18. The A26 drill's "controlled test branch".**

    - a planted defect;

  - **Recommendation:** run it in W3 on a branch from the base, record it under `test-evidence/DG7/orchestrator/a26/`, and keep its findings in a drill-local file, never `findings.json`.
