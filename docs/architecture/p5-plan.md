## 1. Inventory: the 78 DG5 requirements, one slice each

### 1.1 The slices

The P5 row suggests six groups (Studio and builders; rule builder and automations; reports and exports; launch plan and health check; demo; acceptance). This plan keeps them, with four changes, each for a reason:

- **Studio is split into three slices.** A = configuration versioning, publish pipeline, pinning, migration and re-approval (the engine every other slice publishes through). B = form schemas and the common form framework. C = procedure definitions and instances. Together they hold 20 rows, too many for one ~2 h architecture run, and B and C are different engines (field validation vs a step machine).
- **Automation is split into two slices.** D = the rule engine and its operations (versions, dry-run, failure queue, retries, service identity, human-only boundary). E = the starter automations and the approval/notification policies they drive (sequential/parallel routes, conditional approval, quiet hours, cut-off agendas, dependency slips). D is a platform; E is domain rules on it (the P4 slice-I precedent).
- **The KPI/formula remainders form their own slice (G):** prospective/restated KPI changes, formula preview and the optional NPV/ROI/payback extension. They are kpi-benefits work on the P3/P4 engines, not Studio work.
- **The methodology reader, provenance labelling, navigation and branding form one slice (I),** because they share one concern: what the published methodology and the shell say to the user, in en and ar, and that it is true (REQ-PB-001 scan, REQ-S21-001 scan, F-DG4-160).

## 2. Dependencies and order

An arrow `X → Y` means Y needs X's data, contract or service before Y can be finished. Event- or port-coupled pairs (Y implements an interface X defines, or consumes X's outbox event) are marked `⇢`; they let X land first without calling Y.

```text
DG1–DG4 (approved)
   │
   A  Studio core: config versions, drafts, publish pipeline, pin resolver, migration, re-approval
   │
   ├──► B  Form schemas, field types, custom fields, form framework
   │     │
   │     └──► C  Procedures (input schema = a B form; steps route through A's resolver)
   │            │
   ├──► D  Rule engine, failure queue, retries, service identity, jobs view
   │     │      │
   │     └──► E  Starter automations as rules, approval routes, conditional approval, notification policy
   │            ├ ⇢ H (action "generate launch plan" is a port H implements; S12-004)
   │            └ ⇢ C (procedure step due/overdue reminders are rule actions)
   │
   ├──► F  Reports, snapshots (record the A versions), exporters, presentation, owner updates
   │     │
   │     └──► G  KPI restatement (reissue = a new F snapshot version), formula preview, NPV/ROI
   │
   ├──► H  Launch plan, Day-90 test, health check, scoring schemes (scheme versions published through A)
   │
   └──► I  Reader, search, provenance, source links (A's published text; C's "Launch"), navigation, branding (F reads branding)
                 │
                 ▼
          J  Demo seed and walkthrough (needs every engine above: it seeds all of them)
                 │
                 ▼
          K  A02, A06, A07, A15, A16 executable tests; DLV-037 evidence
```

- **Critical path:** A → B → C → D → E → J → K. A's resolver and publish pipeline are used by B, C, E (routes), H (schemes) and I; C's procedures are triggered and reminded by E's rules; J seeds every engine; K proves them end to end (A02 needs the walkthrough, A06 needs A+B+E, A07 needs A+F+G). The ARCH tasks are ordered A, B+C, D+E, F, G+H, I+J (§4); the implementer waves follow the same order (§5).
- **Off the critical path:** F (exports are long, but only J's demo reports and K's A15 wait for them; F starts in W6), G (small, after F's snapshot service), H (pure scoring and dating; E's S12-004 reaches it through a port), I (reads A and C; branding feeds F's templates through a read port).
- **No module cycle.** `methodology` exposes a `ConfigResolver` port (pinned version per transformation and kind) that `forms`, `procedures`, `automation`, `workflows`, `health` and `reporting` call; `methodology` imports none of them. `automation` executes actions through an `AutomationActionRegistry` that each domain module registers into at composition (`server.ts`), so `automation` imports no domain module (the P4 `GateFactsProvider` pattern, ADR-0035 §2).

## 6. Risks and open questions

### Open questions for the orchestrator or the user

- **Q1. How does Studio version a single-version catalogue?** Master prompt l.243: "Protect stable system identifiers and core data invariants"; l.245: "Keep published versions immutable. Existing transformations remain pinned to their methodology and form versions". The DG2 catalogue keys are global (`gate_definition_code_key UNIQUE`, `tom_dimension_code_key UNIQUE`, `gate_criterion_definition_key_key UNIQUE`, `0011`). **Recommendation:** keep the catalogue rows as the stable-identity registry (their `code`/`key` never change: S06-006), and store versioned attributes (labels, help, approvers, routing, checklists, extension fields) in version-scoped rows keyed `(config_version_id, stable_key)`, resolved through the transformation's pin (§3 rows 1, 4). Additive; no DG2 constraint changes.
- **Q2. Conditional approval "disabled by default" vs DG4.** REQ-S04-011: "When enabled in Studio, an approver may approve with conditions"; notes: "Extension (not in playbook); disabled by default". DG4 (ADR-0035 §5) accepts `scaleScope.conditions` on every approved G5. **Options:** (a) seed the Studio switch **on** for the shipped methodology v1 so DG4 behaviour is unchanged, with "disabled by default" meaning the default for a newly authored methodology version (additive); (b) seed it off, so DG4-valid G5 requests with conditions get 422 (reopen). **Recommendation:** (a), recorded in ADR-0044 with the documented reason.
- **Q3. Which starter automations may an admin disable?** REQ-S12-002: "enable/disable them"; master prompt l.394: "Automatic preparation, routing, calculation and reminders are mandatory." **Recommendation:** each of the sixteen seeded starters is configurable (thresholds, recipients, cadence, through a new rule version) but cannot be disabled or deleted when it implements a DG2–DG4-approved guarantee (gate routing, next-phase enabling, KPI recalculation, Finance queue, escalation, BAU reviews); only the optional parts (the 90-day plan, digests) and admin-authored rules can be disabled. Any other answer is a reopen of the DG4 rows those starters complete.
- **Q4. "Creates and reads each one through the API" for fixed catalogue entities.** REQ-S16-012/S16-015 acceptance: "an integration test creates and reads each one through the API with authorization enforced" (MethodologyVersion, Phase, GateDefinition, TOMDimension). REQ-S02-001 requires exactly 6 phases, 6 gates and 10 TOM dimensions, and REQ-S06-006 refuses deleting a TOM dimension or changing a stable ID. **Recommendation:** for these catalogue entities "create" means creating a draft methodology version that contains them (a version-scoped row of an existing identity, through Studio); a seventh gate or eleventh dimension is not creatable. Needs the orchestrator's reading.
- **Q5. Which text is "verbatim" for the Day-90 test and the health-check bands?** REQ-PB-087: "all six questions render verbatim"; REQ-PB-092: "map to the four band texts verbatim". The playbook texts (B0136–B0141, B0152, e.g. "Strong transformation discipline; focus on value acceleration and continuous improvement.") differ from the master prompt's paraphrase (l.416 "shared case/North Star; …"; l.446 "21–25 strong discipline with focus on value acceleration/improvement"). The launch plan differs too: B0134 "Wave 1 evidence" vs l.414 "pilot evidence"; health question 4 "3-5" (B0150) vs "3–5" (l.427). **Recommendation:** render the playbook text (it is the authoritative methodology, CLAUDE.md "Sources") and treat the master prompt as a paraphrase.
- **Q6. Day numbering of the 90-day plan.** REQ-PB-086 acceptance: "with start date 2026-10-01 the Days 31-60 tasks fall between 2026-11-01 and 2026-11-30". This fixes day _d_ = start date + _d_ **calendar** days (day 0 = 2026-10-01, day 31 = 2026-11-01, day 60 = 2026-11-30, day 90 = 2026-12-30), not working days. **Recommendation:** adopt it; tasks keep the calendar due date and show a working-day warning when it falls on a non-working day (no silent shift).
- **Q7. Demo isolation and packaging.** REQ-S18-001: "Demo data lives only in a separately initialized demo environment that never shares a database with production". The P5 owners (stage-plan l.153) do not include devops-engineer, but a separate database or compose profile touches ADR-0011 packaging. **Recommendation:** P5 builds the demo mode as a separately initialized database selected by configuration (CLI `seed-demo`/`reset-demo`, refused when `MTH_ENV=production`) and a documented compose profile change requested from the orchestrator (devops), additive.
- **Q8. Export libraries, fonts and their evidence (blocking risk).** REQ-S13-005 needs "actual PDF, DOCX, XLSX, PPTX and CSV exports"; REQ-S13-009 "bundled fonts". The workspace has no PDF, DOCX, XLSX or PPTX library installed (`node_modules` holds only Playwright 1.56.1 among candidates; the pnpm store was not searched), and the runs are offline. The solution-architect rules require verifying official docs, support windows and licences before pinning. **Decision needed:** the user or orchestrator provisions registry access (or a vetted offline package set and an OFL-licensed Arabic+Latin font) for ARCH-04 and BE-M/BE-N; without it those checks are BLOCKED, and the A15 inspection cannot run.
- **Q9. What does a migration "re-approval" do to an approved gate?** REQ-S06-008 acceptance: "the migration preview lists the new required field and a required G2 reapproval; historical records remain unchanged". **Recommendation:** executing the migration keeps the approved G2 decision and its snapshot in history, marks the gate "re-approval required" and creates a new G2 submission task; work in later phases continues, but the next gate (G3 onward) cannot be submitted until G2 is re-approved. Whether later-phase work should instead be blocked is a business choice.
- **Q10. Restatement authority.** REQ-S07-016: "a restatement of Q1 without authority is rejected". The sources name no role. **Recommendation:** the approver of the KPI's change request (the DG4 KPI change route of S07-015) holds `kpi_restatement.approve`; the requester cannot approve (SoD default).
- **Q11. Quiet hours and digests with an in-app-only channel.** REQ-S12-025: "a non-urgent reminder due in quiet hours is delivered in the next digest". Email and messaging are P6 adapters (l.392). **Recommendation:** in P5 the digest is one in-app digest notification per user per window; the Notification entity group (REQ-S16-022) still completes at DG6.

- **Q12. Studio-published default weights replace a DG3 database function.** REQ-PB-093: "a transformation created afterwards starts with the new default; an existing transformation keeps its weight set and rubric version". DG3 seeds the defaults inside `p3_instantiate_transformation` with `approval_basis = 'source_default'` and the rationale "Source default weights (B0076): strategic fit 25%, …" (`0024`/`0025`). **Recommendation:** accept a scoped reopen: a new migration redefines the function to read the pinned scoring-defaults version, adds `approval_basis = 'studio_default'` with a rationale naming the published version, and keeps the DG3 output byte-identical while the published defaults equal the source.
