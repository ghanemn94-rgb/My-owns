# P6 architecture plan: slices, seams, architecture tasks and implementer waves

- **Task:** T-DG6-ARCH-00 (solution-architect), 2026-10-26. **Stage:** P6 "Integration and system hardening" (DG6, BUILDING). **Base:** `8480971` on `claude/mobily-transformation-platform-dg5-regate2`; DG5 APPROVED (`docs/delivery/gates/DG5.json`, D-193). `node tools/gates/validate.mjs --historical --stage DG5` printed `PASS gate DG5 (historical)` and exited 0 at the start of this task.
- **What this is:** a plan only. It contains no ADR bodies, no migrations and no contract. Each architecture task in §4 writes its own ADRs, migrations, contract operations and a section of `docs/architecture/p6-work-split.md`. This plan fixes the numbering, ranges, order and file ownership those tasks start from.
- **Sources:** the 48 rows of `docs/delivery/requirements.csv` with `final_gate` = DG6 (their `acceptance` texts are binding); master prompt §15 (l.451–475), §16 (l.477–514), §17 (l.516–524), §19 items 4, 6 and 8 (l.551–555), §20 A01, A12–A14, A17, A20–A22 and the load paragraph (l.573–602), the P6 row (l.618); `docs/analysis/stage-plan.md` "P6" (l.179–205); ADR-0001…ADR-0050; `docs/delivery/environment.md` and the residual decisions D-049 (Keycloak image), D-057 (live registry) and D-058 (live CI); the DG5 carry-forward findings of D-193.
- **Two gate systems.** G1–G6 are business approvals inside the product. Nothing in P6 reads or writes the engineering records DG0–DG7. Product G6 never implies DG7. No agent grants a real business, Finance or IT approval. Demo approvals are synthetic and labelled so (REQ-S21-001). An "IT-approved" provider, store or endpoint in this plan is a configuration slot that Mobily IT fills. No P6 task claims that IT approved anything.
- **Honest live-integration status (binding).** These cannot be exercised live in this sandbox: the enterprise IdP, an IT object store, mail or enterprise messaging, an external or internal AI model endpoint, and corporate data sources. Each is delivered as a contract, a working local test adapter, contract tests and a documented residual in `docs/delivery/environment.md`. None is ever called "live", "integrated with Mobily" or "tested against production".
- **Carried rules (D-078 §3, D-088 §2, D-141, D-193), binding on every P6 task:**
  - shared free-text rules and strict UTF-8; `config.consumes` equal to the request media type (imports and webhooks add `text/csv`, the XLSX media type and `application/json`, each pinned in the contract test);
  - commit-time re-authorisation, and no remote I/O inside a transaction. This applies to every connector call, SMTP send, object-store write, webhook verification and model call: a remote call happens before or after the transaction and is recorded through the outbox. Jobs run exactly once, with advisory locks and unique backstops;
  - decimal-only arithmetic; Unknown/Stale/n/a never shown as 0 or green. Imported values are decimal strings, never floats parsed from a spreadsheet's binary double;
  - bilingual text translated at render time, and true for the release it ships in. Every "planned"/"not yet available" string that P6 makes untrue changes in the task that ships the feature (F-DG4-160);
  - one form-level alert per form; session-bound web actions;
  - harness ports below 32768; verification with the locale unset and with `C.UTF-8`; tests deterministic under load, with explicit budgets of at least 2x the measured loaded worst case where the default 30 s is tight (F-DG5-145/146/151 class);
  - every non-zero exit disclosed; ADR claims enumerated and exactly true, never absolute (F-DG3-100);
  - D-193: assignments carry full 40-hex ids; no candidate file changes after a freeze; `runs/**` and `reviews/**` are never moved or deleted; the full e2e runs on the merged tree before every freeze.

## 1. Inventory: the 48 DG6 requirements, one slice each

### 1.1 The slices

The P6 row suggests about ten groups. This plan keeps them, with three changes, each for a reason:

- **Security is split into two slices.**
  - E (authorization boundary) covers who may read what, on every read path: record views, sensitive records, deep links, evidence after ownership transfer, and the shared read-scope port that search (H) and the assistant (D) reuse.
  - F (request, input and integrity hardening) covers what a request may carry and do: uploads, rich text, CSRF, rate limits, secrets, the uniform API and error contract, integrity and append-only audit.

  E is a read-path engine that other slices depend on. F is middleware and sweeps. Together they hold 10 rows.
- **Operational monitoring is joined with service identities and log redaction (J).** REQ-S16-029 ("a log scan after the test suite finds no secrets or storage URLs; a job's identity cannot read records outside its scope") and REQ-S12-019 (operational exceptions) are both about what the running system reports about itself and under whose identity it acts.
- **Search, tables, saved views, states and concurrency recovery form one slice (H).** These rows share one list/detail interaction model:
  - REQ-S15-010 bulk and inline edits "go through the same validation, authorization and concurrency checks";
  - REQ-S16-026 "compare and reapply";
  - REQ-S15-013 "persist column choices in saved views".

  The visual and accessibility rows stay in I.

## 2. Dependencies and order

An arrow `X → Y` means Y needs X's data, contract or service before Y can be finished. A `⇢` means Y implements a port X defines, or consumes X's outbox event, so X can land first without calling Y.

```text
DG1–DG5 (approved)
   │
   E  Authorization boundary: ReadScope port, sensitive records and grants, deep links, evidence after transfer
   F  Request/input hardening: upload policy, SecretProvider, security suite, audit API, sweeps
   │       (E and F are one ARCH task; F's SecretProvider is used by C and B)
   │
   ├──► J  Service identities (jobs and connectors act through ReadScope), operational exceptions, logs, alerts
   │     │
   ├──► C  Identity (issuer checks, Keycloak realm), S3 evidence adapter, notification channels (SecretProvider refs)
   │     │
   │     └──► B  Connector framework, IntegrationRun, test adapters, outbound writes, deliverable confirmation
   │            │  (credentials = SecretProvider refs; runs act as a J service identity; failure ⇢ J exception)
   │            └──► A  Imports and webhooks (a webhook and a connector run both land in A's staging; commit
   │                     calls the DG4 KPI actual path through a kpi import-target port)
   │
   ├──► H  Global search (ReadScope filter), saved views, drafts, compare and reapply, filters, bulk/inline
   │     │
   │     └──► D  Assistant (retrieval = H search + E ReadScope; citations; no write tools)
   │
   ├──► G  Load dataset and workload (needs every schema it seeds: after A–J migrations), p95 run, fixes
   │
   └──► I  UX/a11y hardening over every screen above; K carry-forward (independent, early)
                 │
                 ▼
          L  A17 test-first (after A/B), A12 (after D), A13/A14 (after B/H), A20/A21 (after D/I), A22 and DLV-038 (last)
```

- **Critical path:** E → H → D → L(A12, A21) runs in parallel with E/F → J → B → A → L(A17), and both join at G (the load run needs the final schema and the search index) and L (QA-E). E is first because three engines read through it. The search index (H), the assistant's retrieval (D) and the jobs' service identities (J) must apply exactly the record-view scopes (REQ-S10-004: "using the same scopes as record views"). Building any of them before the port exists would mean a second, divergent scope implementation.
- **Off the critical path:** C (independent adapters; only B's credentials and channel fan-out wait for it), I (screens are hardened after they exist; the contrast and token work starts early), K (no dependency; scheduled early so the e2e budget sweep stabilises the suite before P6 adds specs).
- **No module cycle.**
  - `access` exposes `ReadScope` (a Kysely predicate builder plus a row filter for non-SQL paths). `search`, `assistant`, `reporting/exports`, `evidence`, `integrations` and `operations` call it; `access` imports none of them.
  - `integrations` writes staged rows and asks an `ImportTargetRegistry` port to commit them. Each domain (`kpi` first) registers a target at composition (`server.ts`), so `integrations` imports no domain module. This is the P5 `AutomationActionRegistry` pattern.
  - `assistant` reads only through `search` and `ReadScope`. It registers no action in any registry, so it has **no write path by construction** (REQ-S17-008).

## 4. Architecture tasks

Each task is sized for about 2 hours of architect work and runs alone on the shared contract files (§5.3). It writes:

- its ADRs;
- its migrations with the P2 guard pattern (`p2_attach_guards`, version step, audit-required triggers, CHECKed statuses) and a guard probe on a real PostgreSQL;
- the Kysely types and catalogue pins;
- its `P6_PERMISSIONS` additions;
- its OpenAPI operations, checked with `openapi:lint`;
- the ERD, data-dictionary and permissions-matrix sections;
- its `p6-work-split.md` section: owners, seams, pending lists, problem codes and exact English texts.

Implementers of a slice start only after its ARCH task is merged.

**Migration numbering.** Migrations `0001`–`0097` exist, and the eight retired P5 gap ids are never filled. Each task owns a contiguous range from `0098`. The architect writes from the low end, and the numbers left in a range are for that slice's implementers (seed, index or enabling migrations), in the order its work-split section names. `0128`–`0133` are held by the orchestrator for repairs.

## 6. Risks and open questions

### Open questions for the orchestrator or the user

- **Q1. Where do "Data > Imports" and the new Administration pages live?**
  - The register: REQ-S17-002/003 `screen_api` "Data > Imports"; REQ-S17-001 "Administration > Integrations"; REQ-S12-019 "Administration > Operations"; REQ-S17-009 "Administration > AI assistant".
  - The master prompt §3 lists 14 areas, and DG5 (REQ-S03-007) approved exactly those 14. "Data" is not one of them.
  - **Recommendation:** put Imports under "Strategy and KPIs" (the KPI data it imports) with an entry also in Administration > Integrations. Treat "Data" as the register's informal label. A fifteenth area would reopen DG5.
- **Q2. "Authorized short-lived links" vs "never pre-signed".**
  - REQ-S16-029: "evidence is served through authorized short-lived links".
  - ADR-0010 §2: "There are never public or pre-signed URLs to the client in the filesystem mode"; REQ-S16-006: "evidence is never served from a public URL".
  - **Recommendation:** a link is an API path with a single-use token valid for a short time (proposed 5 minutes, configurable). It is re-authorized on use, and the bytes are proxied by the API in both storage modes. No object-store URL ever reaches the client.
- **Q3. Sensitive records: which types, who grants, what totals show.**
  - REQ-S10-002: "sensitive records need explicit grants … a sensitive benefit is hidden from a workstream member without the grant"; permissions "grant:TO,ADM (access admin)". The sources name no other type and no rollup rule.
  - **Recommendation:**
    - sensitivity applies to Benefit, BusinessCase and Evidence first;
    - only TO and the access admin grant;
    - a user without the grant sees aggregates that include the value, labelled "includes restricted records", but never the record or its individual value.

    Hiding the value from the total instead would make totals differ per user and is a DG4 reopen. The business must choose.
- **Q4. The upload allow-list (a DG2 reopen candidate, §3 row 3).**
  - REQ-S13-011: "common documents/images with file-type and size controls"; acceptance ".exe … rejected".
  - **Recommendation:** PDF, DOCX, XLSX, PPTX, CSV, TXT, PNG, JPEG and GIF, by magic bytes plus extension, configurable by IT. SVG is accepted for download only, never previewed inline. Files stored before P6 are untouched and are never previewed unless they pass.
- **Q5. Keycloak e2e (D-049).**
  - REQ-S16-007: "e2e tests log in through the Keycloak test realm". The pinned image `quay.io/keycloak/keycloak:26.4` is BLOCKED (quay.io denied).
  - Keycloak is also published as `keycloak/keycloak` on Docker Hub, which the proxy allows. That this is the vendor's own official publication is [UNVERIFIED] offline; ARCH-02 must verify it from official documentation.
  - **Decision needed:** adopt the Docker Hub image pinned by digest, or keep the e2e BLOCKED as a disclosed residual. In the residual case, "a token from another realm is rejected" is still proven with the local fake OP in integration tests.
- **Q6. The S3-compatible test target.**
  - MinIO server is AGPL-3.0 and not to be bundled (ADR-0010 L-1).
  - **Options:**
    - (a) a licence-reviewed store such as SeaweedFS (Apache-2.0) in a test-only compose profile;
    - (b) an in-process S3-protocol fake inside the test suite.

    Both need `@aws-sdk/client-s3` (Apache-2.0) from a registry.

### Risks

- **R1. Sweeps find DG1–DG5 defects.** The route-inventory, response-validation, integrity and redaction sweeps (BE-C, BE-F, DO-D) run over 846 existing operations. Each defect they find is a P6 finding, routed to the owning file. A defect in a DG-approved contract is a reopen candidate. Mitigation: the sweeps land early (W4–W7), so repairs fit before the freeze.
- **R2. Scope leaks in derived data.** A search index, assistant context or export built from a stale or broader copy of the data leaks across transformations. Mitigation:
  - `ReadScope` parity test (§3 row 1);
  - the index stores the scope keys, and the filter is applied at query time, not at index time;
  - the A12 extension covers each path, including a scope revoked after indexing.
- **R3. New dependencies in an offline workspace.** The S3 SDK, an SMTP library and possibly a Keycloak image need a registry (D-049, D-057). Mitigation: every adapter has a port and a test adapter that need no new dependency; a missing pin is BLOCKED and disclosed, never faked.
- **R4. Load results on a shared sandbox are noisy.** Mitigation: the report states machine load during the run, uses at least three repetitions and reports p95 of each. A miss is reported as measured, never tuned away by changing the workload after the fact.
- **R5. AI guardrail claims must be exactly true.** No real model runs in the sandbox, so "the assistant refuses X" is proven against the test adapter and the absence of write paths. ADR-0059 enumerates what is proven (no action registry entries, refused intents, quoted text) and what is not (model behaviour of an IT endpoint).
- **R6. The e2e suite keeps growing.** The F-DG5-145/146/151 class will recur with P6 specs. FE-G's sweep in W8 sets measured budgets first. Every P6 spec states its budget from a loaded measurement (D-173 rule).
- **R7. Behaviour changes in approved screens.** Inbox title redaction (§3 row 6), the upload allow-list (row 3), branding refusal (row 18) and sensitive totals (row 2) change approved behaviour. Each needs the orchestrator's reopen decision before its implementer starts. The waves place them in W3–W6, so a "no" leaves time to re-plan.
- **R8. Demo reset checksums.** Adding demo records (test connector, sensitive benefit) changes the REQ-S18-001 checksums. The adding task re-baselines them and records why.
