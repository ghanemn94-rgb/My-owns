## Decision

### 1. The contrast rule for runtime branding (REQ-S15-003; p6-plan §3 row 18; D-195 accepted)

1. **One evaluation function, in the token package.** `@mth/design-tokens` gains `checkBrandingContrast(primary, secondary, source = tokenSource)` (BE-W, `packages/design-tokens/src/branding-contrast.ts`): it builds the token source with `brand.primary` = `primary` and `brand.deep` = `secondary`, re-derives every `derived` token by its rule (`deriveDarkerShade`, as `resolveTokens` requires), and returns `checkContrast()`'s `pairs` for that source. **Only the declared pairs decide**; the three prohibited pairs are a build-time documentation check of the seeded tokens, and a branded colour that makes a prohibited pair pass is not a failure at runtime. The function is pure and decimal-free (contrast ratios are display measurements, not money or rates; they are stored as `numeric(4,2)` rounded down).
2. **The publish refuses below threshold.** `putBrandingSettings` (BE-W, `admin/branding.ts`) calls the function through the injected `BrandingTokenSource` (the composition root passes it, so `admin` imports no workspace package outside ADR-0002) **after** `checkBrandingRules()` and **before** the transaction. If any declared pair is below its threshold the answer is **422 `branding.contrast_insufficient`** (§6), with one `errors` item per failing pair, and nothing is written. The check is repeated inside the transaction only by the database (`branding_contrast_pair_passes`, §2): the colours are part of the request body, so they cannot change between the check and the commit.
3. **A published version records its report.** In the publish transaction, after the `branding_version` insert, the API writes one `branding_contrast_report` with `pair_count` = the number of declared pairs and one `branding_contrast_pair` per pair (ordinal in the declared order), plus the audit event `branding_contrast_report.recorded` (record type `branding_contrast_report`, record id, no version; after-state: version number, rules, token-source hash, pair count, lowest ratio). The token-source hash is the SHA-256 of the bytes of `packages/design-tokens/src/tokens.json` the server loaded.
4. **What is unchanged.** The seeded tokens, the token route, the derivation, the existing ADR-0049 §11 codes and their order, the lock (class `brandingPublish` 730270, key the organization id), the If-Match rule and the audit events of the version and the head. A version published before P6 is **not** re-checked, rewritten or withdrawn (no migration rewrites published configuration). `GET .../contrast` (§5) evaluates such a version at read time and marks it `not_recorded`, so the administrator sees whether the current colours fail.
5. **Build-time gate kept.** `pnpm --filter @mth/design-tokens run check:contrast` stays the CI gate for the seeded tokens ("fails the build below 4.5:1"). BE-W adds a unit test that the runtime function, called with the seeds, returns exactly the build-time report (same 50 pairs, same ratios).

### 2. Entity and fields (migration `0113`)

| Table | Fields | Rules (each proven by the probe) |
| --- | --- | --- |
| `branding_contrast_report` | `id`, `organization_id`, `branding_version_no`, `rules` (`wcag2x-aa-v1`, closed set), `token_source_sha256` (64 lower-case hex), `pair_count` (1–500), `created_at` (`timestamptz`), `created_by` | One per version: `UNIQUE (organization_id, branding_version_no)` (CR07); composite foreign key to `branding_version (organization_id, version_no)`, so a report names an existing version of its own organization (CR08, CR09); audit required at COMMIT for the record id (CR01); exactly `pair_count` pairs numbered 1..`pair_count` at COMMIT, checked when the report is inserted and when any pair is inserted later (CR02–CR04, CR06); append-only for every role, UPDATE/DELETE/TRUNCATE refused (AO01, AO03, AO05); `mth_app` holds SELECT and INSERT only (INV02) |
| `branding_contrast_pair` | `id`, `report_id`, `ordinal`, `fg_token`, `bg_token` (dotted lower-case token names, ≤ 80), `use` (`text`, `large-text`, `ui`), `fg_hex`, `bg_hex` (`#RRGGBB` upper case), `ratio` (`numeric(4,2)`, 1–21, rounded down), `threshold` (`numeric(2,1)`), `usage_note` (1–200), `created_at` | `threshold` is 4.5 for `text` and 3.0 for `large-text` and `ui` (CP03, CP04); **a stored pair always passes: `CHECK (ratio >= threshold)`** (CP01, CP02, CP10, RL06); one row per (report, fg, bg, use) (CP09) and per (report, ordinal); closed set and format checks (CP05–CP08); append-only (AO02, AO04, AO06) |

- **No state machine.** Both tables are immutable; a report has no lifecycle. "Recorded" and "not recorded" (§5) are derived at read time.
- **What `0113` does not do.** It does **not** require a report for every new branding version, so the DG5 publish path keeps committing until BE-W changes it (BV01). BE-W ships, with its API change, the deferred constraint trigger `branding_version_contrast_required` (AFTER INSERT on `branding_version`, DEFERRABLE INITIALLY DEFERRED: a version inserted after that migration has a report at COMMIT) as the next migration id above the highest shipped file at merge time (D-196 item 2). The probe of that migration proves: a version without its report fails at COMMIT; a version with its report commits; versions published earlier are untouched.
- **Ratios and rounding.** The stored `ratio` is `floor2` of the exact ratio, the value the build-time report prints. Because both thresholds have one decimal, `floor2(r) >= t` exactly when `r >= t`: the stored check equals the exact WCAG comparison (the probe stores 4.49 and is refused, CP10). A ratio is never shown as Unknown: both colours are always known (the version's columns are `NOT NULL` and format-checked by `0089`).

### 3. The greyscale cue test (REQ-S15-003 "status chips are distinguishable in greyscale"; M0300 "always accompanied by labels/icons")

"Distinguishable in greyscale" is proven by **non-colour cues**, not by luminance differences between the status colours:

1. **Component test (FE-F, `components/Badges.test.tsx`):** rendering `HealthChip` for the five statuses gives five distinct icon names and five distinct, non-empty labels in en and in ar; `Unknown` renders the `question` icon and its label. No status uses a blue token (`status.*` tokens are not equal to, or a `ref` of, any `brand.*`, `action.*`, `nav.*` or `focus.*` token: a unit test over `resolveTokens()`).
2. **DOM rule on the axe screens (QA-D, §7):** on every screen of the §7 set, every element with the class `status-chip` contains an `.icon` element and non-empty visible text. FE-F fixes each chip that fails, starting with `Scorecard.tsx:230`.
3. **Greyscale screenshot evidence (QA-D):** for the executive overview and one KPI list in en and ar, a screenshot with `filter: grayscale(1)` applied to `html`; evidence only, the assertion is items 1–2.

### 4. Layout, 1440 px and 360 px (REQ-S15-001, REQ-S15-009)

1. **Above the fold at 1440 px (QA-D, FE-F2).** The viewport is **1440 × 900**. The home page is `/my-work` (`/` redirects to it); the executive page is `/executive-overview`. On each, in chromium-en and chromium-ar, with the SYNTHETIC dev users and a transformation that has at least one open decision, one outcome with a KPI and one next action:
   - the regions labelled **decisions**, **outcomes** and **next actions** (each an element with `role="region"` and an accessible name from the catalogue) have their bounding box's top edge above 900 px and a height above 0, with `window.scrollY = 0`;
   - the page background is the token `surface.page` and the navigation background `nav.background` (computed styles), the "light surfaces and blue navigation" of the acceptance;
   - a screenshot of each is evidence.

   Where a region does not exist yet on one of the two pages, FE-F2 adds it (`pages/my-work/**`, `pages/executive-overview/**` named lines), showing existing data only. An empty region shows its designed empty state, never a blank.
2. **The 360 px flows (QA-D, FE-F2).** Viewport **360 × 800**, chromium-en and chromium-ar, the real stack:
   - **approve a gate item**: the configured gate approver (a SYNTHETIC Sponsor) opens a submitted product gate at `/transformations/:id/gates/:gateCode` and records the decision "approved" with its rationale (the business approval of a product gate G1–G6; never DG0–DG7); a second case approves a P4 approval request at `/my-work/approvals/:approvalId`;
   - **submit a KPI actual**: the KPI owner opens `/transformations/:id/kpis/:kpiId/actuals` and submits a value;
   - **review**: the Finance or KPI reviewer opens the KPI review queue (`/transformations/:id/kpi-review`) and accepts the value.

   In each step: no page-level horizontal scroll (`document.documentElement.scrollWidth <= 360`); every primary action button is fully inside the viewport width; the result is read back through the API (one gate decision and one approval decision recorded; one actual submitted; one actual accepted). The same flows also run at **768 × 1024** for the procedure's "768 px".

### 5. Contract (`docs/api/openapi.yaml`)

- **New operation (1):** `getBrandingVersionContrast` `GET /api/v1/admin/branding/versions/{versionNo}/contrast` (tag `branding`; `branding.configure`; 404 `not_found` when the version does not exist in the caller's organization). ## Alternatives

1. **Darken the brand colours automatically instead of refusing.** Rejected: the primary and secondary colours are "approved" colours (M0301) with an approval reference; silently publishing a different colour would misstate what was approved. The derived shades already adapt (§1.1), and only the pairs that use the colour itself can fail.
2. **Evaluate in the web only.** Rejected: the publish route is the boundary (CLAUDE.md "every mutation needs a server-side … validation"), and a direct API call would bypass a web-only check.
3. **No stored report; refuse only.** Considered. The stored report gives the database rule "a published report never holds a failing pair" and the audit history the administrator and AUD can read. It costs two append-only tables and one read operation.
4. **Treat the prohibited pairs as runtime failures.** Rejected: a prohibited pair documents a combination the UI never renders; a darker brand colour that makes it pass is harmless, and refusing it would refuse accessible colours.
5. **Translate problem `detail` on the API by `Accept-Language`.** Deferred to the orchestrator (§7.3): it would change hundreds of DG1–DG5 problem texts' delivery and duplicate the web catalogue.
6. **A generic `explanations/{kind}/{id}` operation.** Rejected for DG6: every input already has an operation (§8), and a second path to the same data would need its own `ReadScope` parity proof.
