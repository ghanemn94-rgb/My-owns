## Context

As built on `HEAD` `a818587`:

1. The sixteen starters are DG4 (and P5 slice A) handlers; their queues, consumer names, idempotency keys and lock classes are approved behaviour (p5-plan §3 row 9; R3).

5. Meetings have `cutoff_date` (DG4 configuration; p4-plan Q8 "DG5 adds it"); agenda items start `draft` and are published one by one by the chair (`meeting.chair`).

### 1. The sixteen starters as seeded rules (REQ-S12-001 AN-04; D-142 Q3)

**Execution recording.** Event and schedule starters run through one wrapper, `withStarterRule(ruleCode, handler)` (`apps/worker/src/automation/starters.ts`, BE-J), registered in place of each DG4 handler on its own queue: it resolves the rule's effective version, takes lock 730258 on `"<versionId>:<triggerKey>"`, inserts the `automation_execution` (trigger key = the envelope's `idempotencyKey`, or `<schedule code>:<ISO minute>`), calls the DG4 handler **unchanged** (same queue, consumer name, `runOnce` key, lock class and outputs; p5-plan R3) and records one `automation_action_result` with the handler's outcome (`done` → `done`; `duplicate` → `existing`; `skipped` → `skipped`) and finishes the execution `succeeded`, or `failed` on the last attempt (ADR-0043 §5). ### 2. New transformation instantiation (REQ-S12-004, M0224)

`POST /transformations` gains an **optional** `launchPlan: { startDate: date }` member (additive, p5-plan §3 row 15; every DG1 request without it is unchanged) and the outbox payload `transformation.created` gains schema_version **2** (`launchPlan: {startDate} | null`); the v1 consumer is kept for events already in flight. In the create transaction, as in DG2–P5 slice B: the methodology pin (DG2 function, unchanged) and the forms pin (BE-D's initializer). Starter 1's handler then, once per event (`runOnce` with the envelope key, unchanged consumer `starter_automation.v1`):

1. **Phase checklist:** creates the entry phase's `phase_step` rows `not_started` through the same function the DG4 `gates.decided` handler uses when it enables a phase (`apps/worker/src/handlers/gates.ts`; BE-J exports it without changing it), skipping rows that exist.
2. **Role-assignment tasks:** for each source role SP, BO, WL, FIN and TO with no assignment in the transformation, one `role_assignment` work item to the creator (`createdBy`), due `roleTaskDueWorkingDays` working days after the creation business date on the organization's default calendar (Unknown due date, `null`, when no calendar exists; never guessed), dedupe `role_assignment:<transformationId>:<roleCode>`.
3. **Optional 90-day plan:** when `launchPlan` is present, calls `LaunchPlanPort.generate(tx, { transformationId, startDate, idempotencyKey: "launch_plan:<transformationId>" })`, implemented by BE-P (ADR-0048; day *d* = start date + *d* calendar days, D-142 Q6). Until BE-P merges, the port is a no-op that records the action result `skipped` with `automation.port_unavailable`, and BE-J's "with the plan flag" test stays in `p5-pending-be-j` (p5-plan §5.2).

A retry or replay creates nothing more: the `runOnce` ledger, the work-item dedupe keys and the port's key (REQ-S12-004 "a retry creates no duplicates").

### 3. Conditional approval as a Studio extension (REQ-S04-011; D-142 Q2)

- **The switch** is the `gate` element attribute `conditionalApprovalEnabled` (boolean) of the methodology kind (ADR-0039 §2; BE-K adds it to the `gate` Zod schema in `packages/shared/src/schemas/studio.ts`, one named line). Resolution for a gate in the transformation's pinned version: the element's attribute when present; otherwise the **catalogue default**, which is `true` for **G5** (DG4's behaviour, ADR-0035 §5, kept for every DG4 transformation pinned to v1: D-142 Q2 option (a)) and `false` for G1–G4 and G6 ("disabled by default").
- **Off:** a G5 decision whose `scaleScope.conditions` is non-empty while the resolved switch is false is refused 422 `gate.conditional_approval_disabled` (named lines in `workflows/gates.ts`, BE-K after BE-C). This changes a DG4 outcome **only** for a version where an administrator has turned the switch off; with v1 it never fires (D-142 Q2, scoped reopen). Conditions on gates other than G5 stay refused as in DG4 (`scaleScope` is G5-only).
- **Never unrestricted scaling:** an approved G5 always carries its `scaleScope` (DG4 422 `gate.scale_scope_required`, unchanged, REQ-S04-011 "a conditional approval with no scope is rejected"), and a scale transition outside the scope stays refused by DG4 (A08 "limited to one region blocks a scale transition for another region").
- **Tracked to closure:** the condition's owner closes it (`POST …/gate-conditions/{conditionId}/close`, `gate_condition.close`, note 3–2000 characters, optional evidence id) into the append-only `gate_condition_closure` (one per condition, owner only; GC01–GC04, GC09); the condition's open `gate_condition_due` work item is completed in the same transaction. Status is derived: `closed` (closure row), `overdue` (open and today in the transformation's time zone is after `due_date`), else `open`.
- **Overdue conditions escalate:** the schedule `gate.condition_escalation_scan` (daily 01:00 Asia/Riyadh) records one `gate_condition_escalation` per overdue open condition (once: UNIQUE, GC07, GC08; never for a closed one, GC05; `overdue_since` = due date + 1, GC06) and one urgent `gate_condition_overdue` work item to the G5 decision's approver (`gate_decision.decided_by`), dedupe `gate_condition_overdue:<conditionId>`. The escalation decides nothing.

### 4. Sequential and parallel approval routes (REQ-S10-015, M0213)

- **Configuration** is Studio's (no new admin write): an `approver_route` element with stable key `approval.<approval_type>` and `approverRoleCodes` (2–6 business roles; technical admins and AUD refused, ADR-0039 §2) with `mode` `sequential` or `parallel`, resolved through the transformation's pin; for procedures, the definition's `approval_mode`/`approval_role_codes` (ADR-0042 §2). `GET /admin/approval-routes` lists the resolved routes of a published version (`methodology.read`). With no such element, or `mode = any`, an approval is the DG4 single-step approval with no route rows.
- **Instantiation:** when an approval of a routed type is created (DG4 `requestApproval` or a module's internal create; BE-K's named lines in `workflows/approvals.ts`), the steps of its current round are inserted (`approval_route_step`; `round_no` = the approval's, `approval_route_step_current_round`, RS11): sequential → step 1 `active`, the rest `waiting`; parallel → all `active` (RS02, RS03). Each activated step creates one `approval_decision` work item per holder of the step's role in scope (dedupe `approval_route:<approvalId>:<round>:<step>:<userId>`). **Sequential: step 2 is not notified until step 1 approves** (its work items are created only when it is activated, and activation is refused before every earlier step is approved: `approval_route_step_sequence`, RS05); **parallel: all are notified at once**.
- **Decision:** `POST /approvals/{approvalId}/route/steps/{stepNo}/decision` (`approval.decide` in the approval's scope, holder of the step's role or its DG4 delegate; `If-Match` on the approval; locks 730226 `approvalSubject` then **730260** `approvalRouteStep`). Outcomes `approve`, `reject`, `request_changes` with a note. SoD: the requester never decides a step when the type is `requester_excluded` (RS06), and one person decides at most one step of a round (RS08). Completion: every step approved → the approval is decided `approved` through `decideApprovalInTx` (BE-C's export) with the last decider; one `reject` → approval `rejected`; one `request_changes` → approval `changes_requested`; in both cases the other open steps become `cancelled`. A resubmission (DG4 round + 1) creates the next round's steps. DG4 `POST /approvals/{id}/decisions` on a routed approval is refused 422 `approval.decide_through_route`. Routed approvals exist only from P5 on; every DG4 approval has no route rows and is decided as before.

### 5. Notification policy (REQ-S12-025, M0241; D-142 Q11)

Four separate settings, each in its own place:

| Setting | Where | Default (= DG4 behaviour) |
|---|---|---|
| Business-day timing | `notification_policy.non_urgent_working_days_only` (organization) | `false` |
| Quiet hours | `notification_preference.quiet_hours_start/end` (user; `time`, may span midnight), else `notification_policy.default_quiet_hours_*` | none |
| Digest | `notification_preference.digest_mode` `off`/`daily`/`twice_daily` and `digest_time`, else `default_digest_mode` | `off` |
| Urgent escalation | `work_item_kind.urgency` (`urgent` for `approval_escalated`, `executive_decision_escalated`, `approval_overdue`, `gate_condition_overdue`; G05) and `notification_policy.urgent_delivery` = `immediate` (the only value in P5) | — |

**Delivery decision** (pure function `packages/shared/src/notifications/delivery.ts`, BE-L; called by both `createWorkItemOnce` twins — API `tasks/service.ts` and worker `kit.ts`, named lines with the parity test — and by the `notify`/`escalate` actions): (1) an urgent notification is `delivered` at once (the database refuses holding it: `inbox_notification_urgent_immediate`, NP01); (2) otherwise, with the effective settings (user row, else the organization policy, else none): inside quiet hours (in the user's time zone) → `held` until the next digest time after the quiet hours end when a digest is on, else until the quiet hours end; outside quiet hours with a digest on → `held` until the next digest time; on a non-working day of the organization's default calendar when the policy says so → `held` until 08:00 of the next working day; else `delivered`. A held row carries `deliver_after` (NP02). The **work item itself is never held**: My Work shows it at once; only its notification waits.

**Digest job** (`notification.digest`, every 15 minutes, BE-L): for each user with held rows due, take lock **730261** on `"<userId>:<windowStart>"` (the 15-minute slot), create one digest notification (`is_digest = true`, message key `notifications.digest`, params `{count}`, link `/me/notification-digests/<id>`) and its `notification_digest` row (UNIQUE `(recipient_user_id, window_start)`, NP07; append-only, NP08), and move the held rows `held → digested` (NP06); with digest `off`, due held rows move `held → delivered` instead. `delivered` is final (NP04); urgency and the digest flag never change (NP05). The DG4 inbox list shows `delivered` rows (all DG4 rows, G04); held rows appear when delivered, digested rows inside their digest. REQ-S12-025's literal case: a non-urgent reminder created in quiet hours (digest on) is delivered in the next digest; an urgent escalation is delivered immediately.

Preferences: `GET/PUT /me/notification-preferences` (`notification.preferences`; every role except AUD; `If-Match "0"` creates; quiet start ≠ end, NP09; organization = the user's, NP10; known time zone, NP11). Policy: `GET/PUT /admin/notification-policy` (`notification_policy.configure`, ADM_TECH; one per organization, NP14). Email and messaging stay P6 adapters; no workflow depends on them (M0241).

### 6. Meeting cut-off draft agenda and pack (REQ-S12-015, M0235)

The schedule `governance.meeting_cutoff_scan` (daily 00:30 Asia/Riyadh; starter 12) finds meetings in status `scheduled` whose `cutoff_date` is today or earlier (meeting time zone) and whose `scheduled_date` is today or later, without a pack, and for each (lock-free: `runOnce` key `meeting_cutoff:<meetingId>` plus UNIQUE `meeting_cutoff_pack_once_key`, MP03):

1. reads the **current open asks** of the meeting's forum through the governance read used by the DG4 agenda (BE-L2 names it; an open ask is an executive decision request of the transformation that is not decided and not already on this meeting's agenda);
2. creates one `draft` agenda item (`executive_ask`, linked decision) per open ask, next free ordinals;
3. inserts the `meeting_cutoff_pack` (`draft`; `as_of`, `cutoff_date` = the meeting's (MP01), the `open_asks` snapshot and the created `agenda_item_ids`; content never changes, MP05) and one `meeting_pack_review` work item to the chair (else the secretary; with neither, no work item and the pack shows "No reviewer assigned").

**Review before publication.** The chair (`meeting.chair`) or the secretary (`meeting.prepare`) of that meeting marks the pack reviewed (`POST …/meetings/{meetingId}/cutoff-pack/review`, `If-Match`; `meeting_cutoff_pack_reviewer`, MP06, MP07; `draft → reviewed` only, MP08). Until then the database refuses publishing any agenda item of the pack (trigger `agenda_item_cutoff_review`, MP04; API 422 `agenda_item.pack_not_reviewed`); items outside packs, i.e. every DG4 item, are unaffected. Publishing stays the DG4 per-item publish by the chair. The pack is a draft from current data; the issued pack snapshot is slice F's (ADR-0045).

### 7. Critical dependency slip (REQ-S12-012, M0232)

- **Detection (API, in the transaction that changes a predecessor's milestone forecast or approved date; BE-J's `portfolio/slip-events.ts` and one named call line in the DG4 milestone update):** for each dependency whose predecessor (`from_kind = 'initiative'`) is the changed initiative, compute the predecessor finish before and after with the DG4 function `predecessorFinish` unchanged (ADR-0023 §5). It is a **slip** when the finish moves later by at least `minimumSlipDays` calendar days, and **critical** when the dependency is on the transformation's critical path (`schedule-network.ts`, ADR-0031) or the new finish is after `needed_by`. A critical slip inserts one `dependency_slip` (slip key `<predecessor initiative id>:<schedule version>`, once: DS04; `slip_days` = after − before, DS01; `critical_reason` consistent with `needed_by`, DS02; append-only, DS05) whose `affected` lists each dependent initiative reachable through the dependency graph with its owner and its forecast finish before and after, computed by the DG4 scheduling functions unchanged, and writes the outbox event `dependency.slipped` `{slipId, dependencyId, slipDays}`.
- **Notification (worker, starter 9):** one `dependency_slip` work item and notification per distinct affected owner (dedupe `dependency_slip:<slipId>:<userId>`): "each affected owner once". A predecessor finish that cannot be computed (no dated milestone) raises no slip; a dependent's forecast finish that cannot be computed is `null` in `affected` and shown **Unknown**.
- **Forecasts** stay computed on read (DG4): the moved dependent forecasts are what the DG4 schedule read returns after the change; the slip row keeps the before/after evidence. No forecast is stored or overwritten.

### 11. Decimal and Unknown semantics

No money or rate is stored by this slice. `slip_days` is an integer count of calendar days; an uncomputable predecessor finish is Unknown (`null`) and raises no slip. A role task due date that cannot be computed (no calendar) is `null`, shown Unknown. A condition's overdue state uses the transformation's time zone; quiet hours and digest times use the user's time zone (default Asia/Riyadh). A route's progress is shown as "step n of m", never as a percentage.

## Alternatives considered

1. **Re-implementing the starters inside the engine.** Rejected: it would change approved DG4 code paths, keys and outputs (p5-plan R3). The wrapper records executions around the unchanged handlers.
2. **Letting an administrator disable any starter.** Rejected by D-142 Q3 and M0242 ("Automatic preparation, routing, calculation and reminders are mandatory").
3. **The conditional-approval switch off by default for v1** (D-142 Q2 option (b)). Rejected: DG4-valid G5 requests would start failing.
4. **Route steps as separate approvals.** Rejected: the canonical approval stays the one decision record (CLAUDE.md "one decision model"); steps are its children.
5. **Holding the work item in quiet hours.** Rejected: a held task would hide due work in My Work; only the notification is held.
6. **Storing recomputed forecasts on a slip.** Rejected: DG4 computes forecasts on read; a stored copy would drift. The slip keeps before/after evidence only.

## Consequences

- Every starter's behaviour stays DG4's; what changes is that each run is recorded as an execution of a versioned rule and that its declared settings can change through a reviewed version.
- `POST /transformations` and the `transformation.created` event gain an optional member and a v2 schema (additive; DG1 requests unchanged).
- The inbox list filters by `delivery_state`; because every DG4 and default row is `delivered`, DG4 results are unchanged (G04).
- BE-K and BE-J edit named lines of DG4 files (`workflows/gates.ts`, `workflows/approvals.ts`, `portfolio` milestone update, `apps/worker/src/handlers/gates.ts` export, `tasks/service.ts` and `kit.ts` twins); each edit is listed in p5-work-split §E with its regression test.
