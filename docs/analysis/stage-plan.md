# Stage plan: P0–P7 (software delivery stages DG0–DG7)

Produced by transformation-analyst (task T-DG0-AN-03). Revised in T-DG0-AN-05 for findings F-DG0-001 and F-DG0-203 and the §21 evidence recheck. Sources: master prompt §21 (M0401–M0416), §0.2 (M0027), §0.1 (M0013) and `docs/delivery/stages.json`. These are engineering delivery stages. They are not the methodology phases or the product gates G1–G6 (M0412).

## Rules that apply to every stage

- **Order.** Stages run in order. A stage starts only after the previous gate is APPROVED; read-only discovery is allowed earlier (M0401, REQ-DLV-040). Before the first write task, run `node tools/gates/validate.mjs --stage DG(n-1) --historical` (REQ-DLV-024).
- **Gate loop.** Every stage ends with the full loop: plan, implement, integrate/freeze, three independent reviews, findings, repair, reverify, audit (REQ-DLV-014, REQ-DLV-010).
- **Concurrency.** At most **4 active workers**. Concurrent writers use separate worktrees with explicit file ownership. The following are single-owner and serialized:
  - migrations;
  - the API contract (OpenAPI);
  - shared configuration (CI workflows, Compose, environment templates, i18n catalogues' key schema, design tokens);
  - the demo seed.
  Two agents never edit the same file concurrently, and only the orchestrator integrates (REQ-DLV-008, REQ-DLV-009).
- **Reviews.** The three reviewers of a round run in parallel against one frozen candidate. release-auditor runs after them.
- **Scope lists.** Regenerated by AN-04 (T-DG0-AN-04) from the merged `docs/delivery/requirements.csv`, covering every area (`REQ-PB`, `REQ-DLV`, `REQ-S01`…`REQ-S21`). The merged register is authoritative; the gate record's `final_gate_ids` must equal the set of rows with that `final_gate`.
  - Partial increments: a row may deliver part of its behaviour in an earlier stage (listed under "increment in Pn that complete later") and be fully verified only at its final gate. A dependent row may rely on that earlier increment; AN-04 checked that no row needed complete by an earlier gate's acceptance scenario completes later (see `acceptance-map.md`).
  - §21 evidence recheck (AN-05). Each "Evidence required before approval" clause (M0403–M0410) was checked against the `final_gate` of the rows that prove it; the results are in the "§21 evidence recheck" section below. It found and fixed three mismatches:
    - REQ-PB-049 was split, and the new admin part is REQ-PB-093 (DG5).
    - The G1–G4 procedure rows now prove invalid approvals are rejected.
    - REQ-S12-020/021 moved to DG5.
- **Executable acceptance tests (AN-05, finding F-DG0-203).** Each A-scenario's executable test (`REQ-S20-001`…`-028`) is authored in the stage that first delivers the scenario. That can be earlier than the gate at which the test must pass, and never later. Two kinds of author write it:
  - **qa-verifier** writes the scenario suite **test-first, before the candidate freezes**, under `tests/qa/**` and `e2e/**`. This follows agent-protocol.md "Write scopes", and the suite becomes part of the candidate.
  - **The stage's implementers** write the unit and integration tests for the rows they build. These tests join the same suite.

  Each later stage extends and re-runs the suite (regression rule M0066/M0413). P6 extends the A01–A22 suites and re-runs them on the DG6 candidate; it is not the first place they are written. Tests written during a review of a frozen candidate go under `docs/delivery/test-evidence/<DGx>/qa/tests/`, and the orchestrator promotes them into `tests/qa/` in the next stage. The per-scenario owners and stages are in "Executable acceptance-test ownership" below.
- **Recurring obligations.** Protocol requirements with increments P0–P7 and final gate DG7 apply at every stage. They are REQ-DLV-005, -008, -009, -010, -011, -012, -014, -018, -021, -024, -027, -028, -030, -031, -039 and -040 (16 rows). Since T-DG0-AN-07 they appear in every P0–P6 "increment in Pn that complete later" list, so each list equals the register exactly, and they complete under P7/DG7. The lists are generated by `python3 docs/analysis/tools/check_counts.py --write` and checked by the same script without `--write`, which exits non-zero on any mismatch.
