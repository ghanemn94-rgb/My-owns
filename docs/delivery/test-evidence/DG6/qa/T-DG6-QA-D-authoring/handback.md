## 5. Findings (proposed; the orchestrator allocates IDs)

- **QA-D-1, Medium, `mandatory_violation: false`, REQ-S17-009 (evidence instrument).**
  - ADR-0059 §12 names "one call each in `apps/api/src/server.ts` and `apps/worker/src/main.ts`" of `installConnectionLog`. At `HEAD` `ea4c122` neither file (nor any file in `apps/*/src`) calls it.
  - Reproduction: `grep -rn installConnectionLog apps/*/src` returns nothing; `grep -rn connection-log apps/api/dist apps/worker/dist` returns nothing.
  - **Expected:** `MTH_CONNECTION_LOG` set on the API/worker produces the log. **Actual:** it produces nothing unless the module is preloaded from outside. QA-D used `e2e/support/connection-log-preload.mjs` to produce the evidence; the preload changes no product behaviour.
- **QA-D-2, Low, `mandatory_violation: false`, REQ-S17-009.**
  - For an outbound TCP attempt that never connects, the connection log writes `{"host":null,"address":null,"port":null}`. The destination of a failed call, which is exactly the offline case, cannot be identified from the log.
  - Reproduction: `mutations/connlog-telemetry.log` and `mutations/connection-log-mutant.jsonl`. The API process opened `net.connect({host:"192.0.2.10",port:443})`; the logged line was `{"at":"2026-10-30T23:32:45.666Z","process":"qa-preload:api/dist/main.js","channel":"net.client.socket","host":null,"address":null,"port":null}`.
  - **Expected (ADR-0059 §12: "with what is known"):** at least the requested host and port. The checker treats an unknown destination as a failure, so a pass is never claimed for it.
- **QA-D-3, severity for the orchestrator to set (High if it is a product regression, since it breaks a required workflow), REQ-S17-003 / REQ-S12-019 (A17; QA-A's suite, not authored or analysed by QA-D).**

## 6. Mutation checks (acceptance 5): no product file on disk was changed
