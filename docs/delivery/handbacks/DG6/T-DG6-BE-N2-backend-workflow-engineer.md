## 2. Behaviour delivered, per requirement

### REQ-S17-006 (owner of the slice part: BE-N2)

> Acceptance (requirements.csv, verbatim): **"A13;A12: replaying an outbound write with the same key produces one downstream effect; a write without confirmation stays 'pending confirmation'"**. Procedure: "Outbound writes require a specific permission, carry an idempotency key and are marked done only on a confirmed response".

| Acceptance element | How it is delivered | Proof (`outbound.test.ts` unless named) |
|---|---|---|
| Same key → one downstream effect | Transaction 1 runs under lock 730313. If a write with the key asks for the same thing (transformation, deliverable, action, and the payload SHA-256 over canonical JSON, so key order does not matter), it is returned with **200**: no new row, no dispatch, no audit event. A different request under the key gets **409 `outbound_write.idempotency_key_reused`**. The dispatch always carries the stored key, so the downstream deduplicates. | "replays the same key and payload (keys in another order)…" checks `testAdapterEffects(connector, key) === 1`, 1 row, and an unchanged audit count. "refuses another request under a used key…" |
| … including after a crash between steps (§B/A.7 tests) | The crash seam throws after the adapter call and before transaction 2. The dispatch happened (1 effect); the write stays `requested` (v1). A replay returns it without dispatching. `confirmOutboundWrite` re-dispatches with the same key and gets `confirmed`, with effects still 1. A crash during a confirm leaves the write unchanged, and the next confirm finishes it. | "a crash between the steps (A13)" (2 tests) |
| Without confirmation → stays "pending confirmation" | Only an adapter outcome `confirmed` with a usable reference (1–200 characters, no invalid character) gives `confirmed` (with `external_reference` and `confirmed_at`). `accepted_unconfirmed`, `no_response`, an adapter error, an unresolvable secret or a timeout leave the write `pending_confirmation` (or `requested` if nothing was sent). A confirm that gets no confirmation writes nothing and audits nothing. | "confirm: never -> pending_confirmation…" (the list filter shows it pending, never under `confirmed`). "a stopped adapter … and a failing adapter … leave the write pending". "a confirmed answer without a usable reference is no confirmation (pending)" |
| Marked done only on a confirmed response; no manual confirmation | `confirmOutboundWrite`'s body is the empty `OutboundWriteConfirm`; any property is 400. There is no "mark confirmed" path. A definitive `rejected` gives `failed` with its code. | "confirm needs If-Match … its body is an empty object (400)". "a definitive rejection -> failed" |
| Confirmed and failed never change | 409 **`outbound_write.final`** (checked in transaction 1 and again in transaction 2). The `0104` guard also refuses a direct `UPDATE`. | "a confirmed write: 409 … and the database guard refuses a direct change". "… then 409 outbound_write.final" |
| Specific permission (`outbound_write.execute`, TD only) | The execute gate gives **403** to a caller who holds the code nowhere (KDS, ADM_TECH, AUD, outsiders). Then comes the transformation read gate (**404**: a TD of another transformation), then the code at the transformation (403). The gate is re-checked inside transaction 1, after the lock, on reloaded grants. Reads need `outbound_write.read` through `ReadScope`: TL gets 403; AUD, TO and KDS read; outsiders get 404. | "KDS, ADM_TECH and AUD get 403 on execute and confirm; nothing is written or dispatched" (also ADM_TECH at organization level, and an outsider). "outsiders get 404 on reads, a TD elsewhere 404 on writes…". "the commit-time re-check: a right lost while the request waits is 403 and nothing is written" |
| An action the configuration does not allow → 422; a disabled connector → 409 | The action must be listed by the **current** configuration: **422 `outbound_write.action_not_allowed`** (`/actionCode`). A connector that is not `enabled` gets **409 `connector.disabled`**. A replay of an existing write still answers after a disable, with no dispatch. | "an action the current configuration does not list -> 422; a disabled connector -> 409". "a replay still answers after the connector is disabled…" |
| Idempotency key | Required in the body (8–200 characters, the contract pattern); unique per connector. | contract exercise (400 for `short`) |
| No remote I/O inside a transaction (rule 4) | During the dispatch, the `requested` row is already committed (visible from another connection), and lock 730313 can be taken by another transaction (`pg_try_advisory_xact_lock` → true). | "during the dispatch the write is already committed and the outboundWrite lock is free" |
| Every mutation (rule 4) | **Authorization at commit time:** shown above. **Validation:** zod body; payload ≤ 16 KiB (400 `validation.too_big`); a key named like a secret at any depth gives 422 `connector.secret_value_refused`; an invalid character gives 400 `validation.invalid_character`. **If-Match** on confirm: 428 when missing, 409 when stale. Execute has no If-Match; it is a create with an idempotency key (ADR-0055 §9). **Audit:** one event per change, with prior and new version, in the same transaction: `outbound_write.requested` (v1), then `outbound_write.confirmed`, `.pending_confirmation` or `.failed`. The trigger-written history is served by `getOutboundWrite`. | "confirms on the adapter's confirmed response…" (audit trail, history, service identity). "the payload rules…" |
| Connector confirmation for REQ-S01-005 (consumed by BE-O) | `setOutboundConfirmationPort` is called once, inside transaction 2, when a write becomes `confirmed`. If it throws, the whole transaction 2 rolls back. Integrations imports no portfolio code. | "calls the connector-confirmation port once, inside transaction 2…". "a port that throws rolls the confirmation back…" |

**Unknown and pending semantics (ADR-0055 §10):** the API returns the raw status, so `requested` and `pending_confirmation` are both pending. `confirmedAt` and `externalReference` stay `null` until a confirmed response. FE-C renders both as "Pending confirmation", never "Done".

## 6. User-facing texts and design notes

- **Texts made untrue:** none. I searched `apps/web/src/i18n/{en,ar}` and the web sources for outbound or downstream-write texts that call the feature planned or later, and found none.
- **Design notes:**
  1. Transaction 2 records the downstream's answer without re-authorizing. The dispatch already happened under transaction 1's commit-time check, and an answer that is not recorded would be lost. It acts as the requesting user for `updated_by` and the audit event.
  2. The execute and confirm gates refuse **403** before the 404 read gate when the caller holds `outbound_write.execute` nowhere. The answer is identical for every transformation id, so it discloses nothing (the `listImportTemplates` `holdsAnywhere` precedent). Without it, ADM_TECH, which holds no `transformation.read`, could only ever get 404, and the §B/A.7 test "no `outbound_write.execute` → 403 (KDS, ADM_TECH, AUD)" could not hold. A TD of another transformation still gets the DG2 404.
  3. `confirmOutboundWrite` asks the adapter with the **write's own** configuration version, not the current one (ADR-0055 §1 "a run … and an outbound write record the configuration version they used").
  4. An unresolvable credential reference sends nothing, so no attempt is counted. An adapter error after sending counts the attempt and leaves the write pending. The error text is never stored.
