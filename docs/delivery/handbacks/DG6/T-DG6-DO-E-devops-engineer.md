## 4. Finding candidate for the orchestrator: the deferred audit check walks the whole `audit_event` index

The candidate: **`p2_audit_required` (migration 0010) cannot use `audit_event_record_idx` fully.**

- **Profile.** I fired the deferred triggers with `SET CONSTRAINTS ALL IMMEDIATE` and `track_functions = 'pl'`, in a
  scratch copy of the generator (`generate/deferred-trigger-profile.txt`). `p2_audit_required` ran **99,333 calls in
  605.9 s, about 6.1 ms each**. The next largest was `kpi_actual_consistency`: 13,013 calls in 5.1 s.
- **Cause.** The function compares `a.record_type = TG_TABLE_NAME`, and `TG_TABLE_NAME` has type `name`. The planner
  therefore keeps only `record_id`, a non-leading column, as the index condition and walks the whole index:
  - with `name`: `Index Cond: (record_id = …)`, `Filter: (record_type = 'initiative'::name …)`;
  - with `text`: `Index Cond: ((record_type = 'initiative'::text) AND (record_id = …))`.

  Evidence: `generate/p2-audit-required-explain.txt`.
- **Impact.** Every audited insert or update, through the API too, pays a cost that grows linearly with `audit_event`.
  At 100,000 events it is about 6 ms per audited row. Bulk operations multiply it, and it will appear in DO-F's update
  p95. Data integrity is not affected; this is performance only.
- **Proposed fix.** For BE-S, in its index and query-fix migration: `CREATE OR REPLACE FUNCTION p2_audit_required()`
  with `a.record_type = TG_TABLE_NAME::text`. That needs the next migration id at merge (D-196); DO-E took none.

Per ADR-0058 §1 and p6-plan R4, nothing in the dataset, workload or infrastructure was changed to hide this. The only
generator change in this area is the in-transaction `ANALYZE`, which gives the product's own checks current
statistics. **The fix belongs to the trigger function.**
