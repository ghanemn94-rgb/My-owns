## 5. For the orchestrator: deviations, contract, schema, dependency

1. **`apps/api/test/integration/admin/security.test.ts` (BE-E's) — two lines.** Joining the class (required by §H/G.2 "rate-limit class `search` via BE-E's `rateLimitClass`") necessarily changes two pins there: (a) the `getSecurityRateLimits` body lists `operationIds: ["searchRecords"]` for `search`; (b) the "every route that declares a class maps to an operation id" test now skips `HEAD` routes: `searchRecords` is the first **GET** in a class, and Fastify registers a `HEAD` twin of every GET with the same config, so the twin carries the class too (correctly: it runs the same handler and is limited with it), but it has no operation in the contract. Expect a merge overlap if another W9 task joins a class (BE-L2's webhook, KBE-A's import upload): the `operationIds` lists must be summed.
2. **Zod mirrors.** No shared mirror of `SearchResultPage` / `SearchIndexStatus` exists in `packages/shared/src/schemas/` (outside my files). The mirrors are restated in `p6-exercises-be-p.ts` (the BE-K precedent). FE-A/FE-D will want shared ones for the web client; adding them is a `packages/shared` change for whoever owns that file.
3. **Interpretations, stated:**
   - **Relevance** "`ts_rank_cd` over the three vectors" is implemented as the **greatest** of the three configurations' ranks (a hit is ranked by the configuration that matched it best), then floored to an integer.
   - **`stale` when `indexedThrough` is null.** ADR-0057 §2 defines `indexedThrough` null "if any is null" and `stale` by status or "older than 120 seconds"; a type whose feed never ran is Unknown, so I report `stale: true` (CLAUDE.md: missing data is Unknown/Stale, never fresh). The shared database's index states are seeded with null `last_incremental_at` by 0108, so until the feed job has run there, every search reads `stale: true`.
   - **Every type's view permission is `transformation.read`.** I checked each of the 12 record views' read gate (`requireTransformationRead`, plus `requireSensitiveRead` for the three sensitive types since BE-B2); the parity test is the proof. The lesson has no item GET; its record view is the transformation's lesson list (`transformation.read`). The P4 cross-transformation `lesson.search` operation is a different, separately permitted view and is not widened here.
   - **A document whose source row is gone** (a hard delete not yet consumed by the feed) is still returned for a non-sensitive type until the next feed run deletes it (BE-P: within a minute); for a sensitive type the party columns are then null, so only grants and the grant permission admit it. I did not join the 9 non-sensitive source tables to hide such a hit, to keep the query on the GIN indexes; say so if you want the join.
4. **503 not in the contract seam.** `searchRecords`' 503 needs every requested type's state `failed`, which is global state shared by the suites that run concurrently on the shared run database (`contract.test.ts` and `response-validation.test.ts` both run these exercises). It is proven on a scratch database in `search.test.ts`; the seam's header says so.
5. **No migration, no new problem code beyond ADR-0057 §10, no contract or `schema.ts` change, no dependency.** FE-A owns the en/ar `problems.json` entries of `search.query_too_short` and `search.index_unavailable` (ADR-0057 §10). BE-P raised that `search.index_failed` (an internal `last_error_code`, shown by `getSearchIndexStatus`) may need an en/ar label in Administration; still open for FE.
6. **`SEARCH_RECORD_TYPES` exists twice** (worker `apps/worker/src/search/documents.ts`, BE-P; API `search/query.ts`, here) because the worker imports no API code and the API's `src` should not import worker code; the unit test pins the API copy to the 0108 set and order.
