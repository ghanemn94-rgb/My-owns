## 3. Decisions on DO-H's questions 1–4

No tool change is requested. `tools/release/**` is untouched.

1. **Repeated headings against "repair by adding sections" (D-243 Q13).**
   - **Decision:** keep the tool's rule of exactly one `## <table>` heading.
   - **How the repair meets it:** each conflicting earlier heading gets the prefix `Earlier section:` (or `Change section:` for a later repeat). That stops it counting as a table heading. One complete generated section is then added. The earlier content is kept word for word, and the repair part's introduction says the generated list wins where the two disagree.
   - **Why:** letting the tool merge repeated headings would accept partial and contradictory lists of one table, for example the P1 `timestamptz` rows next to a later list. IT would then have no single place to read a table's columns.
   - **Disclosure:** the prefix edits the heading text of approved sections. It does not edit their content. ADR-0070 §1 says "never by editing an approved section's **content**", and this is my reading of that line. **The orchestrator should confirm it**, by recording it in `decisions.md` or as an ADR-0070 amendment note, which I did not write because ADR edits are outside this assignment's deliverables. The same applies to the one-line ERD edit, which ADR-0070 §1.1 requires.
2. **Type aliases.**
   - **Decision:** stay strict. A type equals `format_type()` exactly.
   - **Why:** the dictionary should read the way `\d` and the catalogue print, with no alias table in the tool to maintain (`int4`, `varchar`, `timestamptz`, `char(n)` …). The repair sections use the catalogue spelling, so the question no longer causes gaps.
3. **Views under `###`.**
   - **Decision:** keep the `##` rule. The three P1 views have `##` sections in the repair part, and their `###` subsections under "Views (read models)" are left as they are.
   - **Why:** one heading form for tables and views keeps the parser simple and leaves the rule with no exceptions.
4. **Partitions.**
   - **Decision:** confirmed. A partition is covered by its partitioned parent and is not listed.
   - **Why:** a partition has its parent's columns. pg-boss's `job` partitions also depend on which queues exist at runtime (pg-boss creates them, not a hub migration), so listing them would make the dictionary depend on runtime state.
   - **Recommendation:** read ADR-0070 §1's "every base table" as "every table that is not a partition", which is how the tool's header comment already puts it.
