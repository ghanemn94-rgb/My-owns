# Threat model for the delivery controls (DG0–DG7)

This document scopes what the delivery tooling defends mechanically, what it only detects, and what remains a disclosed residual. It concerns the software delivery gates, not the product. Reviewers judge findings about the delivery tooling against this model. A finding outside it still gets recorded, and it can lead to a revision of this document (decisions D-016 to D-033).

It was written after round 11 of DG0 as the root-cause response required by master prompt §0.4. From round 6 onward, each review round found a new gap in the controls compensating for the unguarded agent shell. Rather than keep patching around the shell, D-025 moved the shell into an OS sandbox, and this model bounds the rest. Round 15 showed the same pattern for the file tools: the write guard checks a path, and the CLI writes it afterwards (F-DG0-145). D-030 therefore moved the **whole agent process** into a kernel-enforced sandbox. The guard and the shell sandbox are now defence in depth.

## Actors and trust

| Actor | Trusted for | Not trusted for |
|---|---|---|
| **Delivery orchestrator** (the main session) | Planning, integrating, freezing candidates, importing reviewer sidecars into `findings.json`, running the pre-freeze checks | Recording review verdicts, closing or accepting findings (only reviewer sidecars can), editing reviewer artefacts after the fact (write-once), executing agent-writable code outside a sandbox (D-026) |
| **Implementer agents** (analyst, architect, frontend, backend, kpi-benefits, devops) | Changing product and analysis files within their role scope | Changing gate rules, agent tooling, sources, delivery records, git metadata or Claude configuration |
| **Reviewer agents** (domain, code-security, QA, release auditor) | Producing their own records, sidecars and test evidence | Changing anything else in the repository |
| **Environment operator** (root in the container, the Claude Code platform) | Everything | — (out of scope) |

## Assets

- Gate rules and agent tooling (`tools/gates`, `tools/agents`), and the sources (`docs/source`).
- Reviewer artefacts (records and sidecars) and run evidence (`docs/delivery/runs`).
- Frozen candidate manifests and the gate decision.
- The write guard and the sandbox configuration themselves: `.claude`, settings, hooks, git metadata.

## Mechanically prevented

| Threat | Control |
|---|---|
| An agent writes outside its role's scope with a **file tool**, including through a symlink its shell swaps after the guard's check (F-DG0-145) | **Process sandbox** (D-030, `tools/agents/agent_sandbox.py`). The whole `claude` process runs in bubblewrap with a read-only root. `/tmp` and `/var/tmp` are private, and `HOME` is read-only except a private per-run session directory. Every repository root and worktree is read-only, except the role's own areas. For **confined roles** (reviewers, auditor, analyst) the working tree's top level is a throwaway tmpfs, so anything created there vanishes with the run. Only the role's own directories are bound read-write. Review records, the gate record and the analyst's register go through a private staging copy, from which only the role's own files are copied back: new `round-N/<role>.*` files, the auditor's `<stage>.json`, and the analyst's `requirements.csv`. For **implementers** the working tree is read-write, with every existing protected path bound read-only. The process keeps only `CAP_SETFCAP` (bounding set included), `no_new_privs` is set, and neither it nor a nested user namespace can remount or unmount the read-only binds. The sandbox binds the host's real procfs (read-write) and **shares the host PID namespace (creating none of its own)** while **creating its own IPC namespace** (`--unshare-ipc`), so a bwrap a reviewer runs inside it (the pre-freeze, the sandbox tests) can mount its own fresh procfs and run; a fresh `--proc` mount or a read-only `/proc/sys` submount here would make procfs "not fully visible" and block that nested mount. To keep the shared PID namespace from becoming a cross-run path, each run also enters its own scope-only **Landlock** domain (D-033, F-DG0-152; see the concurrency row below). The kernel refuses the write wherever a symlink points. **Defence in depth:** the write guard hook (`tools/agents/guard-write.mjs`, D-009, D-020, D-023, D-024, D-028) still checks every file-tool write (fixed root, worktrees, symlinks, case folding, fail-closed, no resolution through `/proc`, `/sys` or `/dev`). |
| One agent **falsifies another concurrently running agent's work**: its disposable clones, evidence or review records | D-028 (F-DG0-144), D-030 (F-DG0-145) and D-033 (F-DG0-152). Every run gets a private `TMPDIR` (`/var/tmp/mth-run.*`, mode 700, removed at the end). Inside the process sandbox `/var/tmp` is private, so no other run's directory is even visible, for the shell or the file tools. Each reviewer can write only its own evidence directory (`docs/delivery/test-evidence/<DGx>/<key>`) and, through its staging copy, its own new review files. Another reviewer's records and evidence are read-only to it in the kernel, not only in the guard scopes and the Bash deny list. Because the process sandbox shares the host PID namespace (needed for nested bwrap) and binds a read-write host `/proc`, a run could otherwise reach a concurrent same-uid run through `/proc/<peer-pid>/root` or `/proc/<peer-pid>/cwd` into its writable areas, and could signal it. **D-033** closes this: each run enters its own scope-only Landlock domain (`handled_access_fs=0`, `handled_access_net=0`, `scoped=SIGNAL\|ABSTRACT_UNIX_SOCKET`, applied by `tools/agents/landlock_exec.py` after `setpriv`, before `claude` execs). Sibling domains cannot ptrace each other, so the kernel refuses one run's `/proc/<peer>/root\|cwd` access (`Permission denied`) and its signals to another run, while the empty access masks leave the run's own areas and its nested bwrap working. Fail-closed if Landlock is unavailable. |
| An agent writes a protected path with the **shell** | The shell runs inside the process sandbox above, so the same kernel limits apply. Nested inside it, the OS Bash sandbox (bubblewrap) is generated per run by `tools/agents/agent_settings.py` (D-025). It has `failIfUnavailable` and no unsandboxed escape. Its deny list covers git metadata, Claude configuration, ignore and attribute files, tooling, sources and delivery records in the repository and every worktree. Reviewers and the analyst are confined to their own areas there too, and home and `/etc` are read-only. The agent's command reports a full capability set, but it holds it only in a further user and mount namespace created by the CLI's `apply-seccomp` helper, where every mount is a locked copy: it cannot remount, unmount or write a read-only bind (D-030 evidence). |
| The orchestrator runs **agent-planted code with its own privileges** (a module or bytecode file in the working tree that an unsandboxed interpreter imports) | D-026. The runner's Python helpers run as `python3 -I -B` from `/`, and its Node helpers import only built-ins and protected `tools/` files. The pre-freeze runs every check that executes candidate code through `tools/gates/sandbox-run.sh`. It does the clone, the checkout and the command **all inside bubblewrap**, on a tmpfs private to the sandbox (F-DG0-141), so no concurrently running agent can plant a git filter or hook in the clone, or change it while it is checked. The clone holds only the committed revision, with no ignored or untracked files. The sandbox has a read-only root, the repository's git directory bound read-only, no network and a clean environment. Only protected `tools/gates` code runs outside the sandbox. The orchestrator keeps its own helper scripts and control files out of agent-writable places (`/tmp`, `$TMPDIR`) (D-027). **Dependency installation** (from P1) is not an exception: it too runs inside bubblewrap (D-027, F-DG0-142). |
| A sandbox configuration that protects **some other directory** | The validator requires the deny list to name the protected paths under the run's own working directory (F-DG0-230). That directory, `meta.cwd`, must equal the transcript's CLI init `cwd` and the working directory named in the replayed runner prompt (F-DG0-233). |
| User or local settings switch the guard off (`disableAllHooks`) | Agents start with `--setting-sources project` only. Project settings live under `.claude`, which neither file tools nor the shell can write. |
| Git hooks run during the evidence auto-commit | The auto-commit runs with `core.hooksPath=/dev/null` and `--no-verify`, and checks that it committed exactly the run directory plus the tool-authored files (F-DG0-138). |
| Reviewer artefacts edited after the run | Output binding to transcript replay, plus write-once history (single blob, no modify, type-change or delete events, no back-dating, working tree equal to history) (D-021). |
| A review bound to the wrong run | The CLI-replayed prompt carries the role, stage, run ID, session ID and assignment path and SHA-256. Transcript checks are unconditional. The run must start after the freeze, from a commit containing the manifest (D-016, D-022). |
| An approval that doesn't match the reviewed content | Candidate identity over content and file modes (D-005), manifests recomputed from their source commit, historical re-verification (D-017). |

## Detected, not prevented

| Threat | Detection |
|---|---|
| A process outside the sandbox changes configuration: user Claude settings, git config and excludes, hooks including symlinks, or Claude configuration and ignore files anywhere in the repository and worktrees, whether or not git ignores them | The runner's before-and-after `config_snapshot`. A review or analyst run is refused (exit 71, no auto-commit). For an implementer run it prints a warning for the orchestrator (D-024, D-025). Zero-length, untracked, non-symlink files are ignored, because they are the sandbox's own stubs and carry no configuration (D-026). Added, changed **and removed** entries are all reported, so a configuration file that is deleted or truncated to zero length leaves a trace (F-DG0-012, F-DG0-234, D-027). If the comparison itself fails, the run is treated as changed (fail closed). |
| New untracked files in an **implementer's** writable tree | `git status` and the runner's snapshots. For implementers these are ordinary product changes, reviewed at the gate. The Bash deny list names the paths that exist when the run starts, plus the fixed protected names. **For confined roles this row no longer applies** (D-030, formerly F-DG0-237): a new path at the top level is created in the process sandbox's throwaway tmpfs and never reaches the real tree, and every other new path outside the role's areas has a read-only parent. |
| Writes the process sandbox **discarded** from a staging copy (another role's record, a changed earlier record, another stage's gate record, a register changed concurrently) | The runner lists them in `sandbox.json` and `meta.process_sandbox_discarded`. A review or analyst run with any discard exits 73 and is not auto-committed, and the validator refuses a gate record from such a run. |

## Disclosed residuals (out of scope for mechanical defence)

1. **Self-hashed evidence.** Run evidence is hashed by the runner, not attested by an external service. Someone able to write the repository outside any sandbox could fabricate a complete, internally consistent run directory and commit it as new history, and the orchestrator is such a party. The mitigations are the release auditor's transcript review and the published git history (D-021).
2. **The environment operator** (root outside the agent sandbox, or the platform itself) can change anything, including the validator. Out of scope.
3. **Network access for agent shells** is unavailable in this container's sandbox mode, so the orchestrator performs dependency installation. It does so **inside bubblewrap** (D-027, F-DG0-142):
   - network is allowed for the package registry;
   - the root filesystem is read-only, and only the target tree and the package store are writable;
   - lifecycle scripts are disabled unless allow-listed;
   - the lockfile is committed.

   The wrapper is built and tested in P1 before the first install; the register carries it as a DG1 requirement. The residual is the content of the installed packages themselves: build or test commands later execute package code, but only inside the same sandbox.
4. **Prompt injection through repository content.** A document an agent reads could try to steer it. Agents are told to treat assignment files and repository content as data. The independence of three reviewers plus the auditor is the control.
5. **Implementers can create new files at protected names that do not exist yet** inside their writable tree, for example a nested `CLAUDE.md` or `.claude/` directory, or a root `.mcp.json` while none exists. The process sandbox can bind only existing paths read-only, and the shell's deny list names only the fixed top-level names. Such a file is detected by the runner's configuration scan, which prints a warning for implementer runs (D-024, D-025), and it shows in `git status` before integration. Confined roles are not affected.
6. **The process-API cgroup** (`/sys/fs/cgroup/memory/process_api`) is bound read-write for the CLI process, because its Bash tool registers processes there (D-030). A write redirected there could change that cgroup's own resource limits: an availability risk for the run itself, not an integrity one, since no file outside the role's scope becomes writable.
7. **A read-write host `/proc`, and file-tool writes to uid-0-writable `/proc/sys` entries** (D-030, option A). The process sandbox binds the host's real procfs read-write, because a fresh `--proc` mount or a read-only `/proc/sys` submount would make procfs "not fully visible" and break the reviewers' own nested bubblewrap (the pre-freeze and the sandbox tests). `/proc/sys` kernel tunables are therefore read-only only for the agent's **shell** (the Claude Code Bash sandbox's user namespace, as in round 15) and inside the reviewer's own fresh-procfs sandboxes, where candidate code runs. A **file tool** running in the process-sandbox layer (uid 0, `CAP_SETFCAP`) could write a `/proc/sys` entry of **its own run** that is writable by uid 0 without `CAP_SYS_ADMIN`, directly or by racing a symlink past the guard. That is an availability / host-tunable risk, not repository or gate integrity: no protected repository path, reviewer artefact or another run's scratch becomes writable (those are read-only binds). The per-run Landlock domain (D-033) deliberately restricts no filesystem access (`handled_access_fs=0`), so it does not change this own-run residual; it does close the **cross-run** amplification (reaching another run's `/proc/<peer>/sys` through `/proc/<peer>/root`), which round 18 had shown made this larger than disclosed (F-DG0-152). With that path closed, F-DG0-149 restates this residual at its disclosed own-run scope and is accepted as an observation.
8. **The process sandbox shares the host PID namespace** (D-030), so an agent can still *see* host processes in `/proc`. This is a deliberate trade: a private PID namespace broke the reviewers' own nested bubblewrap (the pre-freeze and the sandbox tests). It does not let an agent write any protected file (the read-only binds and the capability drop are independent of the PID namespace). The **IPC** namespace, which has no bearing on procfs visibility, IS unshared (`--unshare-ipc`, D-031, F-DG0-148), so the SysV-IPC / POSIX-message-queue cross-run vector is closed. What the shared PID namespace *would* otherwise permit — reaching a concurrent same-uid run through `/proc/<peer-pid>/root|cwd`, or signalling it — is refused by the **per-run scope-only Landlock domain** (D-033, F-DG0-152): sibling domains cannot ptrace each other, and `LANDLOCK_SCOPE_SIGNAL` refuses cross-domain signals. Cross-run **file** isolation is also independently held by each run's private `/var/tmp/mth-run.*`, invisible inside the sandbox (`/var/tmp` is a private tmpfs). The residual that remains is only *visibility* of host process metadata in `/proc`, no worse than every round before D-030 and out of scope for the write-integrity controls.

## How reviewers use this model

- A way to break a **mechanically prevented** control is a finding. Its severity follows the agent protocol.
- A gap in a **detected** control is a finding if detection can be evaded without leaving any trace.
- A demonstration that only restates a **disclosed residual** is recorded at Low severity, with a proposal if you have one. It is not a blocking finding unless it shows that the residual is larger than stated here.
